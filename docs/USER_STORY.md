## 产品前提

**Prompt Defense** 是一款网页版无限 roguelike 塔防游戏。玩家不直接购买、放置或操作炮台。

玩家用自然语言写下策略 Prompt。AI 观察战场与资源状态，自主决定如何购买和部署炮台，并持续操作下去。
逐帧模拟（敌人移动、寻路、索敌、伤害、弹道、渲染）由确定性的游戏引擎负责，LLM 不参与其中。

Hackathon MVP 的核心循环是：

> **制定策略 → AI 执行 → 观察战场 → 暂停 → 修改策略 → AI 改变行为 → 继续战斗**

最终目标是：通过不断调整自己的 Prompt，让 AI 生存尽可能多的波次。

### 长期教育目标（保留自旧版，是产品的「为什么」，不是 MVP 需求）

产品面向正在学习如何与 AI 互动的年轻玩家。教育目标不是让玩家背下 Prompt 模板，
而是帮助他们学会如何向 AI 传达意图：

- 定义目标；
- 提供上下文；
- 设定约束；
- 确立优先级；
- 处理例外；
- 观察 AI 的实际行为；
- 基于证据修订指令。

学习成果应从游戏循环中自然涌现，而不是通过传统课程。游戏首先应该以游戏的身份吸引玩家。

# 第一部分 — Hackathon MVP 用户故事

这一部分是最新、最具约束力的用户故事，对应 Hackathon MVP 范围。

## MVP 用户故事 1 — 第一次进入游戏

### 作为一名第一次进入游戏的玩家

我希望能够快速进入游戏，而不需要注册账号，
这样我可以立即开始体验 Prompt Defense。

### 用户流程

1. 玩家打开网页。
2. 系统要求玩家输入一个昵称：

   > 输入你的昵称

   例如：`Haisu`

3. 玩家确认昵称后进入游戏。

### 规则

- 昵称只是本次游戏中的临时身份标识。
- Hackathon MVP 不建立真正的用户账号系统，因此：不需要密码、邮箱、注册、登录、账号管理。
- 昵称主要用于标识本局玩家，并在最终排行榜中显示玩家身份。
- 整体体验类似街机游戏中的玩家署名。
- 昵称是任意用户文本，排行榜渲染必须转义，禁止 `innerHTML` 直出。

## MVP 用户故事 2 — 选择 Quick Start 策略

### 作为一名刚进入游戏的玩家

我希望能够快速选择一个容易理解的初始策略，
这样即使我还不知道应该如何写 Prompt，也可以马上开始游戏。

### 用户流程

进入游戏后，玩家看到策略输入区域：

> **YOUR STRATEGY**

系统提供示例策略：点击 **Random strategy** 按钮，随机把一条示例填入输入框。示例库里包含多种打法，例如：

- **基地防御**：围绕我方基地建设炮台，优先保护基地附近区域。
- **沿途拦截**：沿敌人的主要行进路线部署炮台，尽可能提前消灭敌人。

玩家可以：

- 直接采用这条示例开始；
- 在示例基础上修改；
- 自己输入新的 Prompt。

一次展示多个可选策略的 Quick Start 列表仍属后续范围。

### 设计原则

Quick Start 不只是文字模板。不同策略应该能够导致 AI 出现可观察的不同游戏行为。
例如「围绕基地建设炮台」与「沿敌人路线部署炮台」应该产生明显不同的炮台部署方式。

## MVP 用户故事 3 — AI 自主执行策略

### 作为一名玩家

我希望提交自己的策略以后，由 AI 自主操作游戏，
这样我可以观察自己的 Prompt 在真实战场中会产生什么结果。

### 用户流程

1. 玩家确认 Prompt（输入框为空时 Start 按钮不可用，没有 Prompt 就无法开局）。
2. AI 根据以下信息制定自己的游戏策略：
   - 当前 Prompt；
   - 当前地图；
   - 当前资源；
   - 当前游戏状态。
3. 随后游戏开始。

玩家不再直接操作炮台。AI 自主完成游戏行为，包括：

- 判断是否购买炮台；
- 选择炮台类型；
- 选择部署位置；
- 使用当前拥有的资源；
- 根据战场变化继续做出决策。

游戏引擎负责正常的塔防运行，包括敌人移动、炮台攻击、伤害计算、路径计算和波次推进。

### 游戏速度

正常情况下游戏以标准速度运行。如果玩家暂时不需要修改策略，可以加速游戏，
让当前策略更快接受后续波次的检验。玩家可以在 **正常速度 / 加速** 之间切换。

### 边界（架构不变量）

- LLM 只能在波次或事件触发下做决策，不按帧调用，也不得进入 game loop 或 `requestAnimationFrame`。
- LLM 只能通过 `src/agent/GameActions.ts` 暴露的动作接口影响战场，
  不得直接读写实体、网格、管理器单例或 game loop 状态。
- 动作合法性由引擎判定，失败原因必须对模型可读（如 `INSUFFICIENT_FUNDS` / `BLOCKS_PATH` / `CELL_OCCUPIED`）。

## MVP 用户故事 4 — 修改策略

### 作为一名正在观察 AI 作战的玩家

当我发现当前策略存在问题时，
我希望能够随时修改 Prompt，
这样 AI 可以在下一个思考时间按我的新策略改变行为。

### 用户流程

1. 游戏正在运行，AI 按当前生效的 Prompt 作战。
2. 玩家发现 AI 的行为不符合预期，于是修改策略 Prompt。编辑**不要求先暂停**。
   例如，原策略「围绕基地部署炮台」，改为「围绕基地部署炮台，同时优先在敌人的主要行进路线上部署减速炮台」。
3. 玩家提交新 Prompt。它进入队列，**在当前波结束、AI 下一次思考时生效**；当前波不受影响。
4. 玩家可以继续观察，也可以点击 PAUSE 冻结战场慢慢读：

   > **PAUSE**

   暂停会完整保留当前战场状态，包括：
   - 当前波次；
   - 基地状态；
   - 当前金币；
   - 已部署炮台；
   - 当前敌人；
   - 当前地图状态。

   恢复必须由玩家手动触发：

   > **RESUME**

5. 每个波次开始前（第 1 波也不例外），游戏暂停进入 AI 的思考时间（`PLANNING`）：
   AI 读取此刻生效的 Prompt 版本，结合当前战场重新思考并下令。
6. AI 思考完成后**自动**开启该波，**玩家无需介入**；新 Prompt 从这一波起生效。

### 四种状态（对玩家可见）

| 状态 | 含义 | 如何离开 |
|---|---|---|
| `IDLE` | **未开始**：模拟冻结，等待玩家写开场 Prompt | 玩家点击 Start |
| `RUNNING` | 本波进行中 | 本波生成完毕 → 进入思考；或玩家 PAUSE |
| `PAUSED` | 玩家主动冻结，用于读战场与写 Prompt | **只由玩家手动 RESUME**，绝不自动恢复 |
| `PLANNING` | 每个波次开始前（含第 1 波）的 AI 思考时间（暂停） | AI 思考完成后自动开启该波，玩家无需介入 |

### 核心规则

- **一个 wave 对应一个 Prompt 版本。** 进入思考时间的瞬间锁定，本波行为不受中途修改影响。
- 修改 Prompt 不会重新开始游戏。波次、金币、基地生命、炮台、敌人、战场状态全部保留。
- **随时可以编辑，不要求先暂停。** PAUSE 的作用是让玩家能安心读战场，而不是编辑的前置条件。
- **PAUSE 不会自动恢复**：必须玩家手动 RESUME。
- 思考时间（`PLANNING`）期间再改 Prompt，顺延到下一波。
- `PLANNING` 的触发点是**每个波次开始前**（含第 1 波），不等待上一波场上清空（残敌随暂停冻结）。
- 思考完成后**自动开波，玩家无需介入**；玩家的手动操作只在 `PAUSED`（自己的暂停）。
- 因此玩家可以直接观察：**下一次思考后，AI 的行为是否真的变了。**

一局中这个过程可以重复发生，直到最终失败：

> 运行 → 观察 →（随时）修改 Prompt → 本波结束 → AI 思考 → 新行为生效 → 继续观察

## MVP 用户故事 5 — 游戏失败与排行榜

### 作为一名玩家

当我的基地最终被摧毁时，
我希望知道自己的最终成绩以及与其他玩家的比较，
这样我有明确的结果来衡量这次策略的表现。

### 游戏结束

当基地被摧毁时：

> **GAME OVER**

本局结束，系统记录本局成绩。Hackathon MVP 的核心成绩指标是：

> **到达的最高波次（WAVE REACHED）**

例如：`WAVE REACHED: 27`

### 成绩记录

至少记录：

- 玩家昵称；
- 到达波次；
- 本局成绩。

系统保存成绩并更新排行榜。

### 排行榜

排行榜按照到达波次进行排名，例如：

| Rank | Player | Wave |
|---:|---|---:|
| 1 | Mini | 31 |
| 2 | Haisu | 27 |
| 3 | CC | 22 |

玩家可以看到自己的最终排名。

### 边界

- 分数与到达波次不得仅凭客户端上报入库。排行榜写入需要服务端可校验的对局证据；
  方案未定之前，宁可暂不做持久化排行榜，也不要上线一个可任意伪造的接口。

## MVP 核心产品闭环与神奇时刻

整个 MVP 最重要的闭环不是单纯的塔防胜负，而是：

```
Prompt → AI Strategy → AI Action → Game Result
   ↑                                      ↓
Prompt Revision ← Human Observation ←──────┘
```

MVP 最核心的产品验证是：**玩家修改 Prompt 后，AI 的后续游戏行为能够发生可观察的变化。**
这既包括局内的策略更新，也包括不同局之间的差异。

这就是本项目的**第一个神奇时刻**（保留自旧版故事 6）：

> **“我改了一句话，AI 改变了行为，我活得更久了。”**

验证方式：同一张地图、同一个随机种子，跑两个不同的 Prompt。
如果旁观者能肉眼看出两个 AI 行为不同，核心创意就成立。
如果产品无法稳定地创造这个时刻，就不应该优先去做额外的系统。

## MVP 范围

当前 User Story 所需要的核心能力：

1. 昵称输入与临时身份；
2. Quick Start 策略；
3. 自定义 Prompt；
4. AI 根据 Prompt 自主操作塔防；
5. 游戏正常运行与加速；
6. 游戏暂停；
7. 局内修改 Prompt；
8. AI 根据新 Prompt 和当前战场重新制定策略；
9. 游戏继续；
10. Game Over；
11. Wave Reached 记录；
12. 排行榜。

当前 User Story **不要求**：

- 正式账号系统；
- 密码；
- 邮箱；
- Coin 经济；
- 支付系统；
- Prompt Fork；
- 多 Agent / Swarm；
- 多模型竞技；
- 完整 Prompt Engineering 教学系统；
- 复杂的长期用户数据系统。

Hackathon MVP 首先需要证明：
**玩家可以用自然语言制定和修改战略，而 AI 会把这些战略转化成真实、可观察的游戏行为。**

# 第二部分 — MVP 之外的方向

以下内容来自旧版用户故事，仍然成立，但**不属于 Hackathon MVP 的承诺**。
它们描述产品未来可以演进成的样子，只有在 MVP 的核心闭环跑通之后才考虑。
此处的每一条都不应被当作当前需求实现。

## 首次启动的叙事

开场界面传达一个基本观念：

> # PROMPT DEFENSE（提示词防线）
>
> 你不控制防御塔。
>
> **你教 AI 如何战斗。**
>
> AI 将独自进入战场，并遵循它从你的 Prompt 中理解的策略。
>
> **你的 AI 能活过多少波？**

> **“我不是在操控角色。我是在训练这个 AI 玩家。”**

## 示例 Prompt 与带脚本的教程

MVP 用 Quick Start 策略承担上手，不要求带脚本的教程局。未来版本可以在必须自己写 Prompt 之前，
先展示一个预先写好的示例 Prompt，并演示一个 Prompt 可以包含不同种类的指令：

> **目标：** 尽可能长时间地保护基地。
>
> **策略：** 在敌人停留在射程内时间最长的地方建造伤害塔。
>
> **资源规则：** 不要花光所有可用金币。至少保留 20% 作为储备。
>
> **例外：** 当出现快速敌人时，优先减速它们。

未来版本的教程可以让这个 Prompt 故意留有一个可理解的缺口（例如缺少对 Boss 的策略），
让 AI 在第 5 波 BOSS 处失败，再用简单语言解释失败原因，并问玩家：

> **在下一局之前，你的 AI 应该学会什么？**

> 状态：教程的确切波次、是否故意让 AI 死亡、示例 Prompt 与教学推进方式均未决定。

## AI 行为的可读性

重要决策会被展示出来，并附上简明解释，例如：

> **检测到快速敌人**
>
> 匹配到 Prompt 规则：“当出现快速敌人时，优先减速它们。”
>
> **AI 行动：建造减速塔**

游戏应展示 **决策摘要和动作**，而不是隐藏的模型思维链。
玩家应能观察到直接的因果关系：**我的指令 → AI 决策 → 战场结果。**

## 通过游玩学习 Prompt 结构

游戏不应该以「第 1 课：Prompt Engineering」开场。Prompt 概念应作为解决游戏问题的工具被引入。
学习推进可以逐渐引入：

- **目标（Goal）**：AI 最终应该达成什么？
- **上下文（Context）**：AI 做决策时，哪些信息是重要的？
- **约束（Constraint）**：AI 必须始终做什么，或绝对不能做什么？
- **优先级（Priority）**：当多个问题同时出现时，哪一个最重要？
- **例外（Exception）**：在不寻常或危险的情况下应该怎么办？
- **验证（Verification）**：AI 应该如何检查它上一个行动是否奏效？
- **反馈（Feedback）**：AI 应该从一局失败中学到什么？

玩家学习 Prompt 结构，是因为这能帮他们活过更多波，而不是因为要求背诵术语。

## Prompt 框架（CO-STAR / GEAR）

**CO-STAR** 这类成熟框架可以作为可选的学习材料或进阶的 Prompt 构建技巧被引入。
游戏不应暗示某一种框架是普遍正确的。

对于塔防环境，未来可能引入一种聚焦 Agent 行为的游戏原生结构，例如：

- **G — Goal**：AI 应该达成什么？
- **E — Environment**：它应该关注哪些战场信息？
- **A — Action Rules**：在特定条件下它应该采取哪些行动？
- **R — Restrictions**：它必须遵守哪些资源、风险或行为上的限制？

> 状态：命名是探索性的，未选定任何框架作为游戏的官方框架。

## 无限 roguelike 模式

游戏使用无穷无尽、越来越难的波次序列，没有固定的最终关卡，直到玩家的防御失败。

同一个策略**不一定**在每一局都产生相同结果：

> **Prompt 决定策略 / 方针。RNG 决定策略所遇到的情境。**

因此，一个好的 Prompt 应该表达可复用的决策规则，而不是记住固定的波次序列：

- 脆弱的指令：「在第 5 波升级加农炮。」
- 通用策略：「当出现高 HP 敌人时，优先选择高单体伤害。」

玩家最终得分是 **到达的波次（WAVE REACHED）**。次要指标可能包括存活时间、使用的 token、
AI 成本、平均决策延迟、行动次数，但这些都不应遮蔽主要得分。

## Coin 经济（已移出 MVP）

旧版设计用 **1 Coin = 1 局** 给每次尝试一个成本，让玩家在再次测试前先想清楚如何改进 Prompt。

> Hackathon MVP 明确不要求 Coin 经济。编辑 Prompt 与重开一局都不消耗资源。
> Coin 是否在未来版本回归尚未决定。

## 查看他人策略与 Prompt Fork（已移出 MVP）

旧版设想玩家可以查看排行榜上更强玩家的成功 Prompt，并：

> **分叉这个 Prompt（FORK THIS PROMPT）**

由此形成 **观察 → 复制 → 理解 → 修改 → 测试** 的学习循环，把排行榜变成共享的策略库。

> Hackathon MVP 不要求 Prompt Fork，也不要求公开他人 Prompt。
> 排行榜只展示昵称、波次与成绩。排行榜在这些方面仍然是竞争性的。

# 核心学习循环与产品北极星

无论 MVP 还是长期版本，游戏最终教的是：

> **意图 → 指令 → 行为 → 观察 → 修订**

玩家不会因为知道 Prompt 术语而获得奖励。玩家因为成功与一个自主 AI 沟通而获得奖励。
教育成果从游戏循环中自然涌现：

> **游玩 → 失败 → 反思 → 写 Prompt → 测试 → 比较 → 学习 → 重试**

玩家的显性动机应该是：

> **“我想训练一个能比你那个活得更久的 AI。”**

在这个动机之下的学习成果是：

> **“我越来越擅长向 AI 表达目标、约束、优先级、例外和反馈。”**

当一位年轻玩家并不觉得自己在上 AI 课，却通过反复游玩，在与 AI 系统沟通意图方面变得可测量地更强时，这款游戏就成功了。
